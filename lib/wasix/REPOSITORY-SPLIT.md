# Engine-independent WASIX repository: evaluation only

Audited 2026-11-04: parity-delivery `25e60218af5d165727f7cdb06439fd61464ef8e4`; checked path-migration candidate `577676bd472e81966926321ec2126c7497b0e7f2`. No source, branch, submodule or repository changes; no builds. Read main AGENTS and all five required docs. Source references below are relative to parity-delivery unless stated. Migration changes `lib/wasixv2` to `lib/wasix`, keeps package names, and puts v1 runtime in `lib/wasix-legacy`.

## Verdict

Feasible now as a repository/dependency extraction of an existing boundary, not a kernel rewrite. The kernel already has no engine dependency. There is no evidence that a new generic engine abstraction, trait rewrite, or relocation of NAPI/SDK is needed. Main remains the Wasmer integration owner. A move still needs agreed layout, independent design review, and real cross-repository validation; this report authorizes none of those implementation steps.

The 21 engine-free crate manifests form a closed normal/build-dependency graph with only registry dependencies outside the group. Their only out-of-group path edges are ABI's dev-dependency on the already separate codegen repository, and vnet-web's native dev-dependency on main's `virtual-net` reference relay. Kernel closure: abi; syscalls -> abi/pages/wait; host -> pages; vfs -> abi/pages/wait; vnet -> abi/wait; wait -> abi; pages -> libc on Unix. Kernel additionally uses async-trait/tracing/futures-util; no Wasmer/VM/compiler path appears. This was checked statically over every manifest including target dependencies, not by a resolved build.

Proof in source: `kernel/Cargo.toml:13`; `kernel/src/lib.rs:1`; `kernel/src/tests.rs:1` already drives the kernel with FlatMemory/TestHost/plain Rust. DESIGN's engine-free goal is implemented, though its claim that only exec/dylink know the engine is stale: api and wasix1 also depend directly on it.

## Concrete ownership and placement proposal

Use a standalone pure workspace, retaining existing leaf names and package names. Suggested root members are `{abi,syscalls,wait,pages,host,kernel,vfs,vfs-mem,vfs-host,vfs-overlay,vfs-package,vfs-web,vnet,vnet-host,vnet-switch,vnet-web,stdio-web,trace,record,policy,checkpoint}/Cargo.toml`; put existing ABI generator submodule at `codegen/`. Existing sibling path dependencies remain valid. New root supplies copied workspace metadata, explicit dependency versions/features, resolver 2, edition 2024, Rust 1.96 pin and a lockfile. This is a proposed location, not an implemented layout. Copy appropriate license/security/contribution/build policy and assign maintainers/release responsibility; do not silently retain wasmer repository metadata as the new origin.

Keep main `lib/wasix/{api,exec,dylink,wasix1}` after the pending rename. Keep `lib/api`, VM/compiler changes, CLI/C API wiring, legacy implementation/types/fixtures, and `lib/napi` in main. Exported crate/package names and facade reexports remain stable. `wasixv2` facade is Wasmer-specific today (`api/src/lib.rs:67` reexports Engine and constructs Store/Module); moving it to the pure repository would destroy the desired boundary.

* External abi/syscalls own guest layouts, syscall types, layers and engine-free host capability contracts. External kernel owns observable process, memory, descriptor, filesystem/network semantics.
* External host/pages/drivers own reusable platform implementations. Engine-independent does not mean OS-independent, no_std, no unsafe code, or runtime-independent at every optional feature. Host's tokio/web/browser implementations are reusable services; no need to duplicate them in main.
* Main exec owns Wasmer imports, Store/Instance lifetime, AsyncFunctionEnvMut, guest memory access, asyncify/EH/control transfer, preemption, engine atomics, actual function/table operations and engine errors. `exec/Cargo.toml` uses wasmer with experimental-async and wasmer-types directly. Wasix1's ABI conversion and Wasmer imports are mixed, so keep the entire crate initially; its layout-only dev-tests also use `lib/wasi-types`.
* Main dylink uses optional Wasmer/wasmer-types/exec dependencies, but defaults to sys; api/wasix1 forward sys/js, enabling them. Its metadata/image/initialization/plan portion is genuinely engine-free under no-default-features (`dylink/src/lib.rs:10`), while artifact/runtime/compile/store are engine-specific. Keep the whole crate in main for smallest extraction. A later separately reviewed split could move planner modules, but must preserve existing public reexports and cannot let pure code depend back on the runtime crate.
* checkpoint is currently a manifest plus documentation-only source stub. It can move with the closure; this is not evidence of implemented snapshot/restore. Windows, wasm64 and snapshot work remain deferred.

## The external interface is already present

`syscalls/src/lib.rs` is the intended kernel boundary, not a C ABI. It exports Syscalls/MaybeFuture, Caller/TaskId, UserMemory, Control and action/resume types, plus CPU, shared mapping, loader and function capabilities. Host/Executor supply clocks/timers/randomness/stdio/background and thread execution; VFS/VNet own driver traits. `pages/src/lib.rs` owns SharedPages/Provider, Unix fd access and host mmap helpers used by both sides.

`Caller` borrows UserMemory plus optional DynamicLinker and FunctionOperations for exactly one invocation (`syscalls/src/caller.rs:8`). Kernel never retains the borrowed engine capability. Defaults preserve unsupported/custom profiles (ENOSYS/EOPNOTSUPP/None); extraction must not accidentally make full engine features mandatory. Control's pending GuestAction values carry execution work without Wasmer types; Binfmt checks image bytes, not engine Modules. LoaderControl/LoaderGate/LoaderReservation/HostMemoryLease are plain Rust contracts even though main implements engine-facing pieces against them.

This interface is substantial and currently evolving: return-to-guest task work/restarts/signals, loader safepoints/admission/retirement, descriptor capture/install, thread completion/release, memory layout/protection and CPU accounting are source compatibility obligations. Treat exact commits as compatible sets before claiming stable semver. A successful crate compilation does not prove these temporal protocols.

`pages` contains native Linux/Android/macOS Memfd and Unix mapping helpers. Those belong with reusable memory objects; main still owns use of those objects inside Wasmer linear memory. `vfs-host/src/lib.rs:24` is currently Linux-only (`O_PATH`, /proc), elsewhere Unsupported; vnet-host uses Unix libc/mio/socket2. Moving repositories does not broaden platform support.

Browser host scheduler is already decoupled by ObjectHooks (`host/src/browser/mod.rs:196`); main `api/src/browser.rs:17` installs Wasmer's prepare/receive/collect hooks. Preserve that seam. Keep browser runtime shared-heap/worker transport and general IO providers external; keep Store/module transport installation and guest/runtime memory tests in main. Host browser tests currently inspect exec build recipe paths, so their engine-related assertions must move to a main integration test rather than create an external source dependency.

## Tests and tooling split

Move all existing pure crate unit/integration tests with their code, especially kernel FlatMemory/TestHost behavior, syscall/layer protocols, VFS name resolution/mount/security, VNet/switch/backends and pure web provider/stdio behavior. Retain native host-filesystem/network tests with external drivers. Test default-free core, host tokio/web/browser feature profiles and wasm32 compilation there. Add/retain a dependency graph guard that rejects Wasmer/VM/compiler normal dependencies for every supported pure feature profile. Pure browser tests still need browser/worker/TLS harnesses; they are not all cheap Rust units.

Keep actual Wasmer execution tests in main: exec memory/fork/signals/preemption, dylink engine-tests, api Machine/custom bindings/retirement/browser tests, wasix1 import/layout/guest tests, CLI/C API/NAPI/SDK integration and compiler backend matrix. All 21 crates' tests moving does not justify deleting main integration coverage.

vnet-web `tests/codec.rs` and `tests/relay.rs` use main `virtual-net` to prove existing protocol compatibility. Smallest cut: move these two reference-integration tests to main (e.g. a dedicated integration test target in retained api tests) and keep synthetic codec/backend tests external. Alternative is a version-pinned published virtual-net dev-dependency, but that couples external CI to its release and transitive virtual-mio crate. Do not copy the legacy protocol implementation or move all virtual-net just to make tests green.

`tests/wasixv2` is already a separate suite submodule, with its own Cargo workspace. Its runner compiles fixtures then invokes a selected Wasmer binary (`src/main.rs`, `src/run.rs`); it is not a pure kernel test suite. Keep its authoritative runner in main, shared via its existing repository for libc/toolchains/other engines. Its guest fixtures and backend-neutral expectations may remain reusable without claiming runner neutrality. Keep full supported v1 compatibility as a required result, not merely v2 libc2 green.

Main Makefile `460..486` already separates wasm core/webhost/engine/exec/wasix1/facade checks, a useful ownership split. Browser CI (`.github/workflows/wasixv2-browser.yaml`) contains producer/toolchain fixtures, Node/browser jobs and path-dependent artifacts; make producer/core jobs run external sources and consumer jobs pin the same revisions. Existing `api/tests/browser/check-features.py` prevents native runtime leakage into browser; preserve/update it. Threaded host build script pins nightly, reads lockfile wasm-bindgen version, assumes repository paths and uses custom std/TLS preparation: relocating scripts without adjusting those assumptions is a real breakage.

CI caveat: `test.yaml:883` still explicitly says full native `make test-wasixv2` must be enabled before shipping. Browser workflow covers a narrower, pinned subset. Extraction must not claim to have fixed that gap. Toolchains/sysroots, expected-failure allowlists and artifact provenance remain required inputs.

## ABI, source pins and release workflow

Generator repository is already distinct: gitlink `c2c28b95e0c403b224f9cf83fa0e6d56a5a2f3a0`; test suite `db968b7f81d2f5a4e60e877a9051240a64ce0f66`; NAPI `e815ca93e0fe0fa22f8f1acbba19b014a6dcf427` at delivery baseline. Generator emits pure abi/syscalls AND main exec imports. `abi/tests/generated.rs:16` currently hardcodes all three outputs and repo-root traversal; it cannot simply move intact because it writes/checks main exec output.

Retain one canonical generator/WIT repository. External core checks/blesses its abi+syscalls outputs; main checks/blesses exec against exactly the ABI source revision recorded by its selected core. Both generated source headers/path constants need relocation support. Keep generated outputs committed. No duplication/forking of WIT. Enforce a matching source manifest containing core revision/version, ABI revision, test-suite revision and guest libc/sysroot/toolchain pins; runtime pin mismatches should fail CI before fixture execution. Guest import ABI and Rust traits are different contracts: stable guest signatures do not imply a semver-compatible Rust capability interface.

Recommended early delivery: immutable git-rev dependencies for all external crates from one repository/source. Main root workspace.dependencies centralizes the revision; every retained crate consumes those same entries. Core internal crates continue sibling paths. Core change PR first validates pure tests and downstream main checkout using candidate core SHA; after core merge, a main pin/lock update passes actual integration. Main engine-only work changes no external pin. ABI changes land in canonical generator first, then coordinated core/main/libc/sysroot changes; no automatic generator drift. During co-development, explicit local [patch] entries for all core packages support a sibling checkout; release/CI runs reject unintended local overrides. No new abstract runtime needed.

Options and tradeoffs:

| Option | Fit and cost |
|---|---|
| Existing monorepo paths | Lowest atomic-change/CI cost; no separate ownership. Valid fallback until extraction gates pass. |
| Sibling path checkout only | Fast developer edits, but non-reproducible without a source pin and CI checkout rule; not a distributable dependency contract. |
| Git rev | Best initial standalone dependency while all crates are publish=false/0.0.0. Reproducible source revision, main lockfile changes and cross-repo pin PRs. Cannot be dependencies of eventually published crates without registry versions. |
| Git submodule + path | Fits existing submodule practice and makes a concrete source pin visible; recursively initializes ABI submodule. Extra gitlink/checkout maintenance, larger main tree, root workspace exclude/inheritance care. An external nested workspace must remain its own workspace; do not glob it into main and accidentally inherit wrong metadata. Reasonable alternate if preserving offline checkouts is decisive. |
| Published crates | Best mature consumer/release experience; requires versions, crate ownership, dependency publication order, package contents validation and explicit compatibility policy. Today every new crate has publish=false/version0.0.0 and only path requirements, so publication is additional release work, not a manifest switch. |

Never mix git/path/registry copies of the same core crate in one consumer graph. Rust traits/types, Arc state and pages' process-global object-id allocator must have one Cargo package identity; duplicate source copies can both break type compatibility and invalidate shared-object identity assumptions. Version alignment alone does not guarantee source identity. Keep workspace dependency features explicit, and validate both default native and browser no-default-features graphs; workspace-wide feature union can hide leakage and tests can unify dev-features differently.

Current main publish script ignores publish=false (`scripts/publish.py:177`); release/update tooling traverses workspace/local manifests. New repository needs its own release process; main's should only pin/consume it, and must avoid walking/bumping submodule manifests. Future facade publication requires publishing its external dependency closure first. Core releases need not track every Wasmer engine release, but supported pairs must be documented and tested.

## NAPI, custom binding and SDK limitations

Keep `InstantiationHook`, `InstanceAttachment`, Abi/AbiInstance, Preparation/Entry and typed FunctionEnv/Store objects in main. `api/tests/custom_bindings.rs` proves state attaches per actual main/side instance, with owning-thread and cleanup behavior. Moving these engine-specific APIs into a nominally pure facade would force Wasmer types into the new repository and create a dependency cycle. External custom syscall/layer implementers still use engine-free Syscalls/UserMemory/Host contracts.

NAPI remains main's submodule plus engine APIs. At this baseline NAPI/C API still have optional legacy wasmer-wasix dependencies; extraction is not their migration. Loader's unsafe HostMemoryPin/HostMemoryLease contracts must keep exact backing/allocation ownership, stable addresses and exclusion until consumers drop; retain pin-vs-logical-range distinctions. Non-Send futures, Store/thread affinity, cancellation, queued cleanup and constructor/finalizer reentry are protocol obligations even across a clean Rust crate boundary. Kernel holds capabilities by borrow, not a Store pointer. New repo placement fixes none of the outstanding native arena/root settlement/provider lifetime problems and cannot count as their acceptance evidence.

SDK/browser facade remains consumer composition around main's Wasmer facade: directory/package mount conversion, stdio/network configuration, async run/signal/shutdown and worker teardown. Reuse external driver interfaces, but do not expose engine-specific runtime/shared-object handles in the pure kernel API. Keep generated JS/wasm artifacts with exact source/wasm-bindgen/runtime heap/ABI revisions and test real producer artifacts, not a synthetic package with matching names.

## Minimal staged path, after explicit design agreement/review

1. Finish/land agreed directory rename independently; freeze exact core/engine/codegen/tests pins after ongoing contexts/closures source work is integrated. Do not use extraction as justification to disturb those worktrees.
2. Review the 21-crate ownership cut, git-rev versus submodule choice, generator split and tests. Establish baseline pass evidence/known deferrals for native, browser and supported v1 compatibility before moving code.
3. Prepare external standalone workspace with unchanged Rust APIs; repair metadata, generation paths, browser scripts and move the two reference integration tests to main. Retain full test sources/history; move no engine crate. Demonstrate no Wasmer source/normal dependency and pure behavior/feature gates.
4. In one coordinated main integration PR, swap core dependencies to one immutable external revision; keep facade/exec/wasix1/dylink names, behavior and reexports. Refresh lockfile, CI paths, docs and any NAPI/CLI/C API generated paths. Run crate tests, lint, CLI build and actual native/browser guest/v1/custom-binding/lifetime integration gates. Require independent design and implementation review before merge.
5. Only after reproducible downstream CI and supported-version policy exist, consider publishing; pure dylink planner extraction or generic engine facade are independent future proposals. Do not combine with Windows, wasm64, checkpoint implementation or new compatibility claims.

Practical cost is mostly loss of atomic kernel/exec changes: cross-repo PR pairs, a tested source-pin tuple, dual generation checks, CI/cache/artifact routing and backports. Benefits are real independent kernel/driver testing and third-party engine consumption. If source contracts are still changing daily, first finish the current compatibility seam work, then extract the existing boundary; pretending unstable traits are already a public stable SDK increases cost without improving isolation.
